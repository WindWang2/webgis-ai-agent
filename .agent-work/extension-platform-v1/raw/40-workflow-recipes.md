# Workflow / Recipe / Task-Family / Conformance System + SessionPlan (extension-platform-v1 worktree)

Design docs: `docs/adr/0101-geoworkflow-recipe-conformance-foundation.md` (recipe DSL V2, packs, compiler, corpus), `docs/adr/0098-semantic-product-families-v2.md` (first-class decision tasks/recipes, warning-code contracts). Core red lines: recipes declare *what a workflow needs* (capabilities, roles, obligations), never tool sequences; all selection/evaluation is deterministic, zero LLM/zero I/O (`app/services/gis_harness/workflow_schema.py:5-19`, `recipes.py:1-10`).

## 2. Recipe / task-family schema

`CartographyRecipe` (`recipes.py:55-92`): `id`/`name`/`description`; `intent_tasks` (TaskType ids, L60); `intent_cartography`; `required/allowed_geometry`; `required/optional_fields`; `eligibility: List[EligibilityRule]` (element, check_points/min_points, requires_geometry/fields, reason_code — L35-45); `preferred_analysis`/`optional_analysis` = capability ids (L67-68); `task_optional_analysis` per-task capability add-ons (L74); `primary_cartography`, `secondary_cartography`, `default_components`, `fallbacks: List[RecipeFallback]` (when/reason_code/use/disable, L47-52), `validation_rules`, `export_profile`, `priority` (default 50, L81); V2: `schema_version` (L84) + `workflow: Optional[WorkflowProfile]` (L87); V3: `ontology_tasks` (L92, must exist in ontology, validated `registry_validation.py:165-169`).

`WorkflowProfile` (`workflow_schema.py:162-180`): `schema_version=RECIPE_SCHEMA_VERSION=2` (L30); `domain`; `workflow_family` (e.g. `hotspot_significance`); `keywords_zh`/`keywords_en` (professional routing words); `data_roles: List[DataRoleRequirement]` (role ⊆ 15-word `DATA_ROLES` L34-53, `required`, `acquisition` ∈ local/data_fabric/user_upload/derived (L54), `capability_hint`, `accepted_artifact_types`, `geometry_kinds`, `missing_policy` ∈ block/degrade (L58), derived reason code `DATA_ROLE_MISSING_<ROLE>` (L96-101), `degrade_disclosure`, `must_not_guess=True` default — L104-123); `obligations: List[ScientificObligation]` (kind ∈ precondition/denominator/temporal/uncertainty/transformation/disclosure L61-69; `precondition_id` must hit algorithm-layer scientific preconditions; `on_violation` ∈ block_method/degrade_with_disclosure/warn L71 — L124-136); `completion_requirements` (dimension ⊆ 7 `COMPLETION_DIMENSIONS` L74-84 — data/analysis/science/cartography/observed_map/methodology_disclosure/uncertainty_disclosure); `fallback_policies` (`WorkflowFallbackPolicy`: reason_code → from/to + `downgrade_class` ∈ equivalent/approximation/proxy/degraded/not_allowed L86 + disclosure + blocks_completion — L146-160); `required_disclosures`; `recompute_dimensions` ⊆ 5 axes (L89); `evidence_requirements`.

Task families: `TaskType` Literal (22 tasks, `intent.py:28-54`) is the family vocabulary; ontology tasks link to them via `family_triggers` (`gis_ontology.py:108`). `WorkflowFamily` (`workflow_families.py:36-55`) is *derived*, not declared: `family_id = "<domain>.<workflow_family>"`, seed recipes each become `seed.<recipe_id>` singleton families (`build_families_from_registry` L96-129); members aggregate capabilities/map_models/data_roles/obligations/keywords. `CompositeRecipe` (base + conditional supporting layers triggered by ontology tasks / cartography forms / supporting_requires_states L57-70) and `ScenarioTemplate` (match_subjects/ontology/scope → preferred_families, candidate_recipes, expected_components, minimal_disclosure L72-93) are hand-declared tuples (`COMPOSITE_RECIPES` L206, `SCENARIO_TEMPLATES` L330).

## 3. Registration, routing, precedence, collision

Registration: `RecipeRegistry.load_builtins()` (`recipes.py:712-742`) — seeds first, then 24 pack modules in name order via `PACK_MODULES`; per-module load with fail-loud aggregation (partial knowledge base refuses service, L726-742). `register()` (L744-768): duplicate id → **keep-first** with warning log (seeds win over packs; packs deterministic by module order, L723-725); builds `_by_task`, `_by_domain`, keyword inverted index (ASCII words match whole-word only, Chinese substring; L833-858), caches per-recipe content fingerprint. Singleton `get_recipe_registry()` builds-then-assigns so failed loads don't leave a half registry (L1011-1021). No runtime unregister/override API — the registry is load-only + `reset_recipe_registry()` for tests.

Routing/precedence: `select_candidates(intent, limit=3, project_verified)` (`recipes.py:927-1005`) sorts by a stable 11-key tuple (documented L900-915): (1) raster geometry-expectation mismatch demotes non-raster families (L958-966); (2) **seed seniority** — if the task is served by any V1 seed (`v1_served_tasks` L813-823), V2 recipes are demoted (generic phrasing keeps historical product families; ADR-0101 §风险); (3) exact task hit; (4) V2 generic penalty (workflow recipe with zero keyword hits demoted); (5) more professional-keyword hits first (inverted index `keyword_hits` L894-912); (6) explicit cartography form signals (`aggregate_grid`/`proportional_symbol`); (7) cartography-intent intersection count; (8) V3 ontology layer — recipes declaring `ontology_tasks` intersected with intent ontology matches (opt-in; undeclared recipes unaffected); (9) project memory boost (ADR-0069 `recipe_outcome` ACTIVE, `project_verified` from turn RuntimeContext, `gis_harness/tools.py:451-456`); (10) `priority`; (11) id lexicographic. Compiler stage 5 reuses this (`workflow_compiler.py:226-243`); stage 7b `plan_candidates` may **reroute** the carrying recipe only when the semantic top-1 is scientifically blocked, rerunning role/qualification stages for the new recipe (L304-324). Scenario templates activate via subject-substring + ontology-task hit (`WorkflowFamilyRegistry.match_scenarios` L509-532). Recipe ids can also be pinned explicitly (`recipe_id` param → `explicit_recipe_override`, compiler L233-239).

Collision behavior: duplicate recipe id = keep-first + log (L744-752); dangling capability/cartography/precondition/ontology/family references are fatal at `validate_gis_library()` (`registry_validation.py:120-186`: unknown capability L123-127, map model L128-130, workflow profile static validation L132-151, ontology task L165-169, family layer L172-185; runtime manifest re-checks and `_fatal`s on `recipe_dangling_capability` `runtime_manifest.py:397-410`). Precedence across systems: LLM hints can only *suggest* (intent hint-protected tasks, ADR-0098 §1); recipes never hardcode tools — CapabilityRegistry/AlgorithmResolver resolve at plan time.

## 4. Conformance corpus

Lives in code, not data files: `CONFORMANCE_FAMILIES` — 59 hand-audited semantic family rows (`app/evaluation/conformance.py:104`, dataclass L70-101 with `phrases_zh/en`, `expected_task/recipe/capabilities/warning_codes/forbidden_warning_codes`, `alternative_recipes/tasks`, `expected_ontology_task`). Expansion is deterministic: 3 seed-phrase languages × 12 `SCOPE_VARIANTS` (L26-41) × 9 `UTTERANCE_VARIANTS` (L45-55) → 20,088 `GISBenchmarkCase`s with stable ids `CF-<family>-<lang><i>-<scope>-<utterance>` (`_expand_family` L616-661, `build_conformance_corpus` L663-686, duplicate-id assert fails fast). Run via `GISBenchmarkRunner.run` plan-tier (task/recipe/capability/warning/ontology assertions; qualification cases invoke `compile_workflow` `runner.py:379-397`; determinism double-run L399-417). Tests: `tests/unit/gis_harness/test_conformance_corpus.py` — full corpus ≥20,000 and green in default lane (L29-53), stratified sample `cases[::37]` (L56-73), domain slices (L75+), all pack domains covered (L87), anti-claim plan cases (L97), 11 workflow contract cases incl. verdict-V2 "perfect render still BLOCKED_BY_METHOD" (L107-127, executor `anti_claim.py:228-317` synthesizes a complete render and requires the downgrade to come only from the workflow contract), V2 compile sweep all 147 pack recipes (L129, `anti_claim.py:320-327`), 7 e2e scenarios (L152). Related lock sets: 306 golden/matrix cases lock the *generic* product families; corpus covers professional workflows.

## 5. SessionPlan / ExecutionPlan relation to recipes

`SessionPlan` (`app/services/session_plan.py:67-78`): per-session envelope keyed `session-plan` in SessionStore; `gis_chapter` = embedded MapProductPlan dump (contains `recipe_id`, `workflow_contract`, `methodology_warnings`, `manifest_fingerprint`, `data_requirements`, `analysis_steps`); `progress: List[CapabilityProgress]` = capability/data-requirement completion, not tool calls (L59-64, `_init_progress` L113-123). Written by `webgis_map_intent` result hook (L601-638): same-goal replace voids old rows (`goal_key` L96-110); new goal archives + supersedes envelope (SSE `session_plan_superseded`). Tool success/failure marks capability rows complete/failed via algorithm-registry tool→capability map (`capabilities_hit_by_tool` L417+). Projection `format_session_plan_projection` (L177-268) prints `recipe=<id> open=...` header + STALE_PLAN flag when `manifest_fingerprint` differs from current runtime manifest (`session_plan_stale` L157-174) — recipe content edits change `RecipeRegistry.content_fingerprint()` (L825-832) → manifest fingerprint → old plans flagged stale (ADR-0101 C12). Runtime plan production bypasses `compile_workflow` (used by evaluation only): `webgis_map_intent` calls `MapProductPlanner.plan_from_intent` directly (`gis_harness/tools.py:455-464, 627-637`); planner stamps fingerprint (L440) and evaluates the workflow contract at finalize (`planner.py:664-667, 1003+`). Verdict: `derive_product_verdict` (`completion/contracts.py:211-288`) — workflow `data_blockers` → BLOCKED_BY_DATA, `method_blockers`/blocking fallbacks → BLOCKED_BY_METHOD even on perfect render (L253-265). Promotion: a successful plan becomes a persistent re-runnable project `Workflow` (`workflow_promotion.py:1-14` → `WorkflowCreate/WorkflowStepSpec`, DB models `app/models/project.py:79,118,147`; capability re-resolved on rerun, resolved tool kept only as evidence).

Not recipe-linked: `ExecutionPlan` (`geocompute/plan.py:217-246`) is the geocompute data-plane DAG (semantic per-node fingerprints, budgets, payload contracts — ADR-0101 D2); `PlanProposal`/plan_mode (LLM-authored multi-tool plan, `plan_mode.py:154-190`) and `CanonicalPlan` (`planning/models.py:111-160`) are separate plan truth paths; the planning package explicitly defers orchestrator integration (`planning/__init__.py:2-7`).

## 6. Extension seams + gaps for a Workflow/Recipe Pack SDK

Seams that already exist:
- Pack contract is tiny and declarative: module exposes `RECIPES: List[CartographyRecipe]`; add to `PACK_MODULES` tuple (`recipe_packs/__init__.py:18-45`); `_kit.py` builders hide boilerplate.
- Compile-time integrity gates make third-party packs safe: `validate_gis_library` (dangling capability/model/precondition/ontology fatal), family-layer validation, corpus semantic-identity locks, parity tests.
- Deterministic fingerprints (`recipe_content_fingerprint`, registry + family + ExecutionPlan fingerprints) give staleness/repro hooks for versioned packs.
- Families/composites/scenarios derive from the registry — new packs automatically gain family projections without a second registry.

Gaps / friction for an SDK:
1. **No external registration path**: packs are hardcoded import modules in `PACK_MODULES`; loading is in-process import at singleton init (`recipes.py:723-742`). No entry-point/plugin discovery, no packaged (e.g. YAML/JSON) recipe format — recipes are Python/pydantic only; no signing, versioning, or dependency metadata per pack.
2. **Keep-first collision is silent-ish** (warning log only, `recipes.py:744-752`); an SDK needs explicit conflict policy (namespace/prefix per pack, override declarations) — currently only module order decides.
3. **Routing precedence is baked into one 11-key tuple** in `select_candidates` (`recipes.py:900-1005`) — no pluggable scoring/weights; seed seniority and V2 generic penalty are hardcoded policy, limiting pack authors' control over their own routing (by design, but a SDK would need a documented, extensible ranking interface).
4. **Corpus authoring is code**: conformance families must be added to `CONFORMANCE_FAMILIES` tuples in-tree (`conformance.py:104`); no per-pack corpus manifest a pack could ship (family/contract/anti-claim cases co-located in `app/evaluation/`).
5. **No pack lifecycle API**: no enable/disable per domain, no per-pack diagnostics beyond `domains()`/`recipes_for_domain()`, no recipe schema-version negotiation (V1/V2/V3 coexist via `schema_version` + additive fields only).
6. **Runtime uses a different entry than the compiler**: tools call `plan_from_intent` directly while the 15-stage `compile_workflow` is evaluation-only (`tools.py:464` vs `runner.py:379`) — contract surface duplication an SDK would need to unify.
7. Project-level promoted workflows (`workflow_promotion.py`) are a separate persisted format from `CartographyRecipe`; no round-trip back into the recipe registry (user workflows can't be routed/validated like packs).
