# WebGIS AI Agent 技术方案说明书

说明本项目"是什么、为什么这样建":一个以 LLM Agent 为交互核心的 WebGIS 分析平台,用户用自然语言发起空间问题,系统规划工具调用、抓取多源空间数据、执行分析并直接在浏览器地图上产出可交付的专题图层与报告。

## 1. 项目定位与目标用户

### 1.1 定位

传统 GIS 工作流把"找数据、洗数据、跑算子、调样式"拆散在多个工具里,门槛高、链路长。本项目把这些环节收拢到一个对话式 Agent 中:LLM 负责理解意图、规划步骤、调用工具;工具层负责真实的空间计算与数据抓取;前端负责把结果即时渲染成专业地图。系统不生成"关于地图的文字描述",而是生成地图本身。

当前形态是一个可自托管的全栈应用:FastAPI 后端 + Celery 异步计算 + Redis + PostgreSQL/PostGIS,前端为 Next.js 14 + MapLibre GL JS。

### 1.2 目标用户

- **专业空间分析者**(城市规划、应急、选址分析):需要快速完成"数据获取 → 空间分析 → 制图出报告"的完整闭环。
- **GIS/数据从业者**:用 Agent 消除爬虫、数据清洗、脚手架代码等重复劳动,直接进入分析本身。
- **探索型用户**:对身边地理问题有好奇心(如"我司周边哪里适合开早餐店"),无需 GIS 背景即可获得可交互的分析结果。

## 2. 总体架构与技术栈

```
┌─ 前端 Next.js 14 (MapLibre GL JS, Zustand) ─────────────┐
│  对话流(SSE) · 图层栈 · 任务中心 · MapSpec 渲染运行时      │
└──────────────┬───────────────────────────────────────────┘
               │ REST /api/v1/* + SSE 流 + WebSocket
┌──────────────▼───────────────────────────────────────────┐
│ FastAPI 后端 (uvicorn :18000)                              │
│  ChatEngine 规划-执行回路 · ToolRegistry 工具体系           │
│  Explorer 探索引擎 · Data Fabric · MapSpec · RAG           │
│  SessionDataManager (会话数据/引用) · 统一 durable job 运行时│
└───────┬───────────────────────┬──────────────────────────┘
        │                       │
   Celery Worker           Redis (broker db0 / result db1
   (重计算: 缓冲/叠加/        / 会话数据存储)
    栅格运算/网络分析)             │
        │                       │
   PostgreSQL + PostGIS ◄───────┘
  (生产; 开发/CI 以 SQLite 兜底)
```

| 领域 | 选型 | 说明 |
|------|------|------|
| 后端框架 | FastAPI + Python 3.12 | SSE 流式对话(`/api/v1/chat/stream`),异步路由 |
| 异步计算 | Celery + Redis | 重型空间算子(缓冲/叠加/栅格)进 worker,不占请求进程 |
| 空间计算 | GeoPandas / Shapely / rasterio / rasterstats / scipy / esda / h3 | 矢量与栅格算子、空间统计、六边形网格 |
| 数据库 | SQLAlchemy 2 + alembic;生产 PostgreSQL/PostGIS(postgis/postgis:15-3.4),开发 SQLite 兜底 | 单迁移链,SQLite 下 render_as_batch |
| 缓存/队列 | Redis 7 | Celery broker/result、限流、会话大对象存储 |
| LLM | OpenAI 兼容接口,默认阶跃 Step Plan `step-3.7-flash`(推理模型) | 可在设置中切换任意兼容模型;规划阶段可单独配 `LLM_PLANNER_MODEL` |
| 前端 | Next.js 14 (App Router) + React 18 + TailwindCSS + Zustand | Node 22 |
| 地图渲染 | MapLibre GL JS + react-map-gl | GPU 矢量渲染,支持 GeoJSON source 与 MVT 瓦片 source |
| 监控 | prometheus-fastapi-instrumentator(`/metrics`)+ Grafana | 部署配置见 `deploy/` |

本地启动、`.env` 配置与三种启动路径见[本地开发手册](SETUP_INSTRUCTIONS.md)。

## 3. 核心概念域

### 3.1 会话与项目工作区

- **会话(Session)** 是一切状态的命名空间:对话历史、地图状态(图层栈/视口/底图)、Fetch-on-Demand 引用、MapSpec 修订,全部按 `session_id` 隔离。匿名会话由 `owner_token` 保护(能力令牌语义),登录会话由 JWT 保护;两者在数据端点上经同一 `require_owned_session` 依赖校验(ADR-0030)。
- **项目工作区(Project)** 是跨会话的组织单元:`/api/v1/projects` 提供项目 CRUD 与数据集、产物(Artifact)的挂载;对话请求携带 `project_id`,Agent 产出可归档进项目(ADR-0049)。

### 3.2 工具体系:ToolRegistry

Agent 的全部能力以工具形式注册进统一注册表(`app/tools/registry.py`)。`app/tools/__init__.py` 声明 34 个静态注册入口,覆盖地理编码、OSM 检索、空间分析、图层管理、遥感、制图、图表、报告、网络分析、时序、空间统计、坐标变换、模板、项目、数据织网等模块,另加动态技能加载(`app/skills/*.py`,Agent 可在运行时编写并热加载技能脚本)。启动时统一注册,单个模块加载失败不阻塞其余工具。

关键纪律(ADR-0006 统一分发、ADR-0043 执行策略):

- 所有工具经统一分发服务执行,带指标采集(ADR-0044)、缓存与 single-flight(ADR-0045);
- 工具返回大 FeatureCollection 必须转存为 `ref:` 引用(见 3.8);
- 工具名在分发点做旧名归一,保持向后兼容。

### 3.3 ChatEngine 规划-执行回路 + Pi Agent 桥

对话主回路在 `app/services/chat/execution_engine.py`(对外以 `ChatEngine` 兼容层暴露),一轮请求的典型生命周期:

1. **上下文组装**:地图状态摘要、图层列表、近期事件日志、计划状态拼进请求消息;
2. **规划**:可选 planner 阶段产出结构化计划(plan 以 `ref:plan-*` 引用落存,别名 `plan-current` 寻址),SSE 推送 `plan_ready`/`plan_step_done` 事件,前端渲染分步进度;
3. **并行工具波**:工具调用按波并行执行,期间有 token 心跳与工具波心跳保活长连接;
4. **观察与自愈**:工具异常被转化为自然语言反馈进入上下文(`construct_self_healing_message`),LLM 据此改换参数或换工具重试;
5. **流式输出**:SSE 逐 token 下发,工具结果卡片携带 `geojson_ref` 等提货凭证。

**Pi Agent 桥**(`app/agent_pi_bridge.py`,ADR-0031):设 `USE_NEW_AGENT=true` 时,对话经 JSON-RPC 子进程桥接给 Pi agent 运行时(stdio 传输,事件由 `pi_event_mapper` 映射回统一的 SSE 事件协议);子进程崩溃或桥不可用时自动回退到 ChatEngine 回路,服务降级而非硬失败。

### 3.4 统一 durable job 运行时

ADR-0052 把三个互不相通的任务状态存储(内存 TaskTracker、无人调用的 `analysis_tasks` 表、进程内 `_task_owners` dict)合并为一个持久任务生命周期:**Agent task → 工具步骤 → 重型 GIS job → Celery worker → 产物**。

- API:`/api/v1/tasks/jobs*`(列表/详情/取消/重试,需先于 `/tasks/{id}` 注册避免路径吞噬),旧 `/api/v1/tasks` 端点保留兼容;
- **取消真正停止计算**:`CancellationToken` 三路传播——流引擎在并行工具波内抢先取消 asyncio 任务;ContextVar 携带进同步 GIS 代码(热循环在 `jobs.checkpoint()` 退出);watchdog 线程兜底;
- 前端**任务中心**(侧栏任务页)消费该 API,展示跨会话任务视图。

### 3.5 空间探索引擎 Explorer

面向"帮我找某类数据并画出来"的开放式需求,`app/services/explorer/` 实现六阶段流水线(ADR-0034):

**意图识别(intent_detector)→ 数据源发现(discover)→ 抓取(fetch)→ 解析(parse)→ 验证(validate)→ 地理编码(geocode)**,外加 quality_engine 做结果质量评估,orchestrator 负责跨重启的链路状态持久化。API 为 `/api/v1/explorer/start|status|abort|stream/{task_id}`,前端通过独立的进度流消费阶段推进,登录会话走属主校验流,匿名会话桥接进会话隔离的聊天流。

### 3.6 Data Fabric 数据织网

`app/services/data_fabric/`(ADR-0050 企业级地理数据织网、ADR-0053 可靠性)是对接外部空间数据源的统一接入层:适配器(Overpass/OSM、政府开放数据、PMTiles/GeoParquet/FlatGeoBuf 等)+ 连接管理、断路器、目录同步、物化服务与安全校验。资源护栏硬限制单次物化规模(`DATA_FABRIC_MAX_FEATURES=50000`、256 MiB 响应上限、分页与超时预算),防止单个远端查询拖垮进程;物化结果同样以 `ref:` 引用进入会话存储。

### 3.7 MapSpec 制图闭环

MapSpec 是"地图的声明式规格":Agent 的制图意图先落为结构化 spec(事务化修订,带 checkpoint),经管线校验/修复(制图语义检查、有效性证据阶梯)后编译为前端可执行的图层运行时(`frontend/lib/mapspec-runtime/`),渲染结果回传 ACK 形成闭环(ADR-0008/0016/0036)。配套能力:制图模板(`/api/v1/templates`)、SVG 导出(`mapspec_to_svg.py`)、统一专题样式契约(`docs/adr/0052-unified-thematic-style-contract.md`)。这让"AI 出图"从一次性截图变成可修订、可回放、可导出的工程产物。

### 3.8 Fetch-on-Demand 与 Data Plane

工具产出的超大 FeatureCollection 不进 LLM 上下文:后端转存为 `ref:geojson-xxxx` 引用(Redis 会话存储,按 session LRU 上限 200 条),LLM 只见引用壳与摘要;SSE 只下发提货码;前端经 `GET /api/v1/layers/data/{ref_id}?session_id=...` 独立拉取,直接注入 MapLibre 原生渲染。超过 5000 要素的图层进一步走 MVT 矢量瓦片显示路径(ADR-0047),`transformRequest` 注入会话凭据。完整机制见[Fetch-on-Demand 文档](data-fetcher.md)。

### 3.9 RAG 知识库

`app/services/rag/`(engine / faiss_store / chunker)提供向量化知识库:文档入库分块、FAISS 检索、注入对话上下文;知识库 API 位于 `/api/v1/knowledge*`,按租户隔离(ADR-0038),索引随源文件 mtime 失效重建,入库失败的向量有补偿清理。

## 4. 前端与可视化

### 4.1 信息架构与视觉体系

当前 UI 是 **Visual System V4(专业 GIS 工作台视觉)叠加 V3 信息架构**,二者都是已落地现状:

- **信息架构(V3)**:左侧 NavRail 导航轨 + ContextPanel 上下文面板(`frontend/components/layout/nav-rail.tsx`、`context-panel.tsx`),地图画布为主体的工作台布局;侧栏承载聊天、图层、任务、结果、数据源等多标签页。
- **视觉体系(V4)**:`frontend/app/globals.css` 中的语义 token 体系(`--surface-*`/`--text-*` 等),暗色主题为一等公民而非亮色的滤镜;对比度经过实测审计(如 muted 文本对比度不足已被修正)。历史上的 V2 玻璃拟态类(`.glass/.ib/.tb/.lc/.sq`)已在 V4 中移除——那是被替换的中间形态,不是当前 UI。

### 4.2 渲染路径

- **小矢量图层**:GeoJSON source + 视口裁剪;
- **大矢量图层(>5000 要素)**:MVT 瓦片 source,按视口请求,凭据经 `transformRequest` 注入;
- **栅格图层**:XYZ PNG 瓦片(`/layers/data/{ref}/raster-tiles/...`);
- **原生热力图**:MapLibre heatmap layer,GPU 插值;
- 地图命令(加层/缩放/样式/标注等)经统一命令目录(`COMMAND_CATALOGUE`)执行,每条命令有显式终态 ACK 回传(防"假成功"),闭环状态存会话存储。

### 4.3 流式交互

对话走 SSE(`/api/v1/chat/stream`),事件协议覆盖 token 流、计划事件(`plan_ready`/`plan_step_done`)、工具结果卡片(含 `geojson_ref` 提货)、地图动作与心跳;另有 WebSocket 通道用于实时推送。前端在会话切换、断线重连、页面刷新后均能恢复(地图状态重建 + 任务轮询恢复)。

## 5. 质量与安全

- **认证**:JWT 登录体系(`/api/v1/auth/*`);`manage.py create-admin` 在关闭公开注册后创建管理员。匿名会话以 `owner_token` 隔离,恒时比较校验,所有会话数据端点强制归属检查。
- **限流**:全站 IP 维度滑动窗口限流(默认 60 请求/60 秒,Redis 实现,内存兜底,`app/core/rate_limiter.py`)。
- **配置校验**:生产模式启动即拒绝缺失 `JWT_SECRET_KEY`、LLM key 占位符、SQLite 数据库与 `CORS_ORIGINS=['*']`;外部 URL 统一做 SSRF 校验(协议/回环/私网/云元数据/DNS 解析)。
- **监控**:`/metrics`(Prometheus)+ `deploy/prometheus.yml` + Grafana dashboard 与告警规则(provisioning);管理端指标摘要 API `/api/v1/metrics/digest`。
- **安全门禁(CI,release-blocking)**:bandit(`bandit -r app/ -ll -ii`)与依赖审计(pip-audit / npm audit)独立 job,失败即阻断。
- **测试体系**:单元/集成/端到端分层;markers `heavy`/`perf`/`cartography`/`real_services` 各有专属 CI lane;后端覆盖率闸 75%,前端有独立覆盖率阈值;制图闭环与性能回归(带基线下限)是发布门禁。
- **数据护栏**:Data Fabric 物化上限、栅格输出资源护栏(ADR-0042)、上传路径校验、地图动作 ACK 上限等,防止大负载与失控循环。

## 6. 非目标

明确不做的方向(避免误解与范围蔓延):

- **不做通用 GIS 桌面软件**:不追求替代 QGIS/ArcGIS 的全量编辑能力;聚焦"对话驱动的分析与制图闭环"。
- **不做后端静态出图**:渲染在前端 MapLibre 完成,后端不维护 Python 出图管线(历史方案已移除);导出走前端截图/打印与 MapSpec SVG 路径。
- **不做通用聊天机器人**:没有空间工具调用的纯闲聊不是优化目标。
- **不承诺离线运行**:LLM 与多数数据源依赖外部 API;本地 SQLite/Redis 只是开发兜底,生产要求 PostGIS + Redis。
- **不做多租户 SaaS 化运营**(当前阶段):有认证与会话隔离,但不做组织/计费/配额体系。

## 7. 演进路线

版本历史以 [CHANGELOG](../CHANGELOG.md) 为准(0.1.x 系列;更早的 V3.x 阶段名是 release-notes 语境下的历史阶段划分,见 `docs/release-notes-*.md`)。已落地的近期里程碑包括:统一 durable job 运行时与取消生命周期(ADR-0052)、Data Plane MVT 瓦片(ADR-0047)、Data Fabric 可靠性(ADR-0053)、全栈性能优化与 52 项开放问题的根因修复批次。

**下一阶段(Phase 6,规划中)**的主要方向:

- 用户认证增强(权限模型与账号体系完善);
- 动态栅格图层(栅格数据源的动态瓦片与样式能力扩展)。

长期愿景保持不变:让空间分析的门楣降到"一句话",同时把专业制图的产物质量维持在可交付水准。
